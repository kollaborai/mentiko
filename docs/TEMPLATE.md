# Technical Documentation Template

Standard template for Mentiko technical documentation.

## Structure

```markdown
# [Title]

[One-line description of what this is]

## Overview

[2-3 sentences explaining what this thing is and what it does]

## Design

### [Key Concept]

[Technical explanation with code examples]

### [Another Key Concept]

[Technical explanation with code examples]

## Characteristics

### Advantages

- [Point 1]
- [Point 2]
- [Point 3]

### Limitations

- [Point 1]
- [Point 2]
- [Point 3]

## [Implementation Section]

[How it works, with code examples]

## Schema

[Data structures if applicable]

## Location

[File paths, directory structure]

## Monitoring

[Metrics, health checks]

## Error Handling

[What happens when things break]

## Related

- [Link to related doc]
- [Link to related doc]
```

## Style Guidelines

**Tone:**
- Technical, factual
- No opinions or comparisons to other systems
- No "we chose X because Y is bad" framing
- Describe the system as it is

**Content:**
- Explain what the thing is
- Explain how it works
- Explain its characteristics (advantages/limitations)
- Provide implementation details
- Show code examples where relevant
- Link to related docs

**Avoid:**
- Blog-style conversational tone
- Comparisons to other systems ("unlike Redis...")
- Opinionated language ("the best choice is...")
- External references or citations
- Marketing language or persuasion

**Code examples:**
- Use real syntax (bash, JSON, TypeScript)
- Keep examples concise
- Show actual usage patterns

**Sections:**
- Overview (what is this?)
- Design (how does it work?)
- Characteristics (what are its properties?)
- Implementation (technical details)
- Schema/Locations (where does it live?)
- Monitoring/Error Handling (operational concerns)
- Related (what else should I read?)
```

## Notes

- All docs follow this template
- Sections adapt based on content type
- Some docs may not need all sections
- Keep descriptions factual and technical
